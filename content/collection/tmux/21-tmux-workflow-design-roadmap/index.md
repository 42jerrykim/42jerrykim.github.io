이 컬렉션의 마지막 장이다. 지금까지 21개 챕터에 걸쳐 배운 세션·윈도우·패널·설정·플러그인·SSH·Vim 통합·트러블슈팅은 각각 낱개의 지식이었다. 이 장은 그 지식들을 <strong>단독 개발</strong>, <strong>원격 서버 운영</strong>, <strong>페어 프로그래밍</strong> 세 가지 실전 시나리오로 조합하고, 이 컬렉션이 의도적으로 남겨 둔 심화 주제로 이어지는 로드맵을 정리한다.

## 이 장을 읽기 전에

**선행 챕터**: 이 장은 [20장: 트러블슈팅](/post/tmux/tmux-troubleshooting-clipboard-colors-nested-sessions/)에 이어, 새 명령을 도입하지 않고 지금까지 배운 모든 것을 세 가지 실전 시나리오로 종합한다.

**이 장의 깊이**: 이 컬렉션 전체를 완주했다는 전제로, 각 챕터의 기능을 실전 조합으로 다시 배치하는 데 집중한다.

## 당신의 수준에 맞는 경로

| 상황 | 읽을 부분 | 핵심 목표 |
|---|---|---|
| 혼자 여러 프로젝트를 오가며 개발하는 사람 | 시나리오 1 | 프로젝트별 세션 구성을 표준화하고 재부팅에도 대비할 수 있다 |
| 여러 서버를 SSH로 관리하는 사람 | 시나리오 2 | 여러 서버 세션을 일관된 규칙으로 관리할 수 있다 |
| 팀원과 화면을 공유하며 작업하는 사람 | 시나리오 3 | 상황에 맞는 공유 방식을 설계할 수 있다 |
| 이 컬렉션을 완주하고 다음 학습 방향을 찾는 사람 | 심화 학습 로드맵 | 이 컬렉션이 다루지 않은 주제를 어디서 이어갈지 알 수 있다 |

## 정신 모델: 워크플로우는 레이아웃과 자동화, 습관의 조합이다

실전 워크플로우는 단일 기능이 아니라 여러 챕터의 조합으로 만들어진다. "어떤 레이아웃을 쓸지"(04·09장), "그것을 어떻게 자동으로 재현할지"(13·14장), "재부팅이나 여러 사람과의 공유 같은 예외 상황을 어떻게 다룰지"(12·16·17장)가 합쳐져야 비로소 하루하루 실제로 쓸 수 있는 워크플로우가 된다. 아래 세 시나리오는 이 조합이 상황마다 어떻게 달라지는지 보여준다.

## 시나리오 1: 단독 개발자 워크플로우

혼자 여러 프로젝트를 오가는 상황에서는 매번 같은 구조를 손으로 다시 만드는 것 자체가 낭비다. 그래서 이 시나리오의 핵심은 "한 번만 정의해 두고 이후에는 이름 하나로 재현하는 것"에 있다.

| 구성 요소 | 선택 |
|---|---|
| 세션 구조 | 프로젝트마다 이름을 붙인 세션 하나(예: `myapp`) |
| 윈도우 구성 | `editor`(04장 레이아웃), `server`, `logs` |
| 재현 방법 | 14장의 tmuxinator·tmuxifier로 프로젝트별 설정 파일화 |
| 재부팅 대비 | 16장의 tmux-resurrect·tmux-continuum으로 자동 저장·복원 |

이 조합의 핵심은 "한 번 설정해 두면 그다음부터는 프로젝트 이름 하나만 기억하면 된다"는 것이다.

## 시나리오 2: 원격 서버 운영 워크플로우

여러 서버를 오가며 관리하는 상황에서는 화면을 예쁘게 꾸미는 것보다 접속이 얼마나 빠르고 안정적인지, 그리고 같은 명령을 여러 서버에 얼마나 빨리 반복할 수 있는지가 훨씬 중요하다.

| 구성 요소 | 선택 |
|---|---|
| 접속 방식 | 17장의 `ControlMaster`/`ControlPersist`로 재연결 속도 개선 |
| 세션 이름 규칙 | 서버 역할이 드러나는 이름(예: `web-01`, `db-primary`) |
| 여러 서버 동시 작업 | 09장의 `synchronize-panes`로 여러 서버에 같은 명령을 한 번에 |
| 불안정한 네트워크 대응 | 17장에서 다룬 mosh 조합 검토 |

이 조합의 우선순위는 단독 개발 워크플로우와 다르다 — 예쁜 상태바보다 접속 안정성과 여러 서버를 오가는 속도가 먼저다.

## 시나리오 3: 페어 프로그래밍·멘토링 워크플로우

다른 사람과 화면을 나누는 순간부터는 "내가 편한 설정"이 아니라 "상대방이 무엇을 보고 무엇을 할 수 있어야 하는가"가 설계 기준이 된다.

| 구성 요소 | 선택 |
|---|---|
| 공유 방식 | 12장의 같은 세션 다중 attach(화면을 완전히 똑같이 봐야 할 때) 또는 세션 그룹(각자 다른 창을 봐야 할 때) |
| 관찰자 참여 | `attach -r`(읽기 전용)로 조작 권한 없이 참여시키기 |
| 접근 준비 | 소켓 권한(12장)을 미리 조정해 다른 계정을 가진 사람도 붙을 수 있게 |
| 화면 크기 차이 대응 | `ignore-size` 플래그로 한 사람의 좁은 화면이 다른 사람 화면을 줄이지 않게 |

이 조합에서는 정보량보다 "상대방이 지금 무엇을 보고 있는가"를 정확히 통제하는 것이 우선이다.

## 자신에게 맞는 조합 고르기

세 시나리오를 가르는 기준은 결국 하나다 — <strong>누가, 무엇을 위해 이 화면을 보는가</strong>. 자기 자신만을 위한 것이라면 재현성과 자동화(시나리오 1)가 중요하고, 여러 대의 기계를 상대한다면 접속 안정성과 동시 조작(시나리오 2)이, 다른 사람과 화면을 나눈다면 통제와 공유 범위(시나리오 3)가 우선한다. 세 시나리오는 배타적이지 않다 — 원격 서버에서 페어 프로그래밍을 한다면 시나리오 2와 3의 요소를 함께 조합하면 된다.

## 주의사항·함정

**처음부터 완벽한 설정을 만들려 하지 않는다**: 11장에서 다룬 재배치 동사(swap·move·break·join)는 애초에 "처음부터 완벽한 배치를 계획할 필요 없이, 작업하다가 구조가 어색해지면 그때그때 정리한다"는 철학을 담고 있다. `tmux.conf`도 마찬가지다 — 한 번에 완성하려 하지 말고, 실제로 써 보면서 점진적으로 다듬는 편이 현실적이다.

**다른 사람의 설정을 검증 없이 그대로 가져오지 않는다**: 07장에서 다뤘듯 커뮤니티에 공유되는 tmux.conf는 특정 터미널 앱·운영체제를 전제로 만들어진 경우가 많다. 그대로 복사하기보다, 자신의 환경에서 각 바인딩과 옵션이 실제로 의도대로 동작하는지 확인하는 과정을 거친다.

**이 컬렉션이 다루지 않은 영역이 남아 있다**: 플로팅(popup) 패널, 제어 모드(`tmux -CC`), 훅(hook) 기반 자동화처럼 이 컬렉션이 의도적으로 범위 밖에 둔 기능들이 공식 문서에 더 있다. 완주했다고 tmux의 전부를 다룬 것은 아니다.

## 흔한 오개념

<strong>"완벽한 tmux.conf 하나만 있으면 모든 상황에 대응된다"</strong>는 생각은 틀렸다. 단독 개발, 원격 운영, 협업은 서로 다른 우선순위(재현성, 접속 안정성, 공유 통제)를 요구하므로, 하나의 설정으로 세 시나리오 모두를 최적화하기는 어렵다.

<strong>"이 22개 챕터를 다 읽었으니 tmux를 다 안다"</strong>는 오해도 있다. tmux 공식 문서에는 이 컬렉션이 의도적으로 다루지 않은 플로팅 패널·제어 모드·훅 같은 고급 기능이 더 있다.

<strong>"설정은 한 번 완성하면 다시 손댈 필요가 없다"</strong>는 생각도 정확하지 않다. 워크플로우 자체가 바뀌면(새 프로젝트, 새로운 협업 방식) 설정도 11장의 재배치 철학처럼 계속 다듬어야 한다.

## 심화 학습 로드맵

이 컬렉션에서 범위 밖으로 남겨 둔 주제를 계속 공부하고 싶다면 아래 순서를 권한다.

1. **플로팅 패널과 제어 모드**: 11장에서 언급만 했던 `move-pane`의 플로팅 전용 옵션과 `tmux -CC`(iTerm2 등 특정 터미널 앱과의 통합)를 tmux 공식 매뉴얼에서 찾아본다.
2. **훅(hook) 기반 자동화**: 13장의 `if-shell`/`run-shell`보다 더 이벤트 중심적인 `set-hook` 계열 명령으로, 특정 이벤트(윈도우 생성, 세션 종료 등)에 반응하는 자동화를 구성할 수 있다.
3. **커스텀 플러그인 작성**: 15–16장에서 다룬 기존 플러그인을 넘어, TPM 규격에 맞는 자신만의 플러그인을 직접 만들어 볼 수 있다.

## 평가 기준

이 컬렉션을 완주한 후 다음을 할 수 있어야 한다.

- 단독 개발, 원격 서버 운영, 페어 프로그래밍 각각에 맞는 tmux 기능 조합을 설계할 수 있다.
- "누가, 무엇을 위해 화면을 보는가"라는 기준으로 워크플로우 우선순위를 판단할 수 있다.
- 다른 사람의 tmux 설정을 그대로 가져오지 않고 자신의 환경에서 검증하는 습관을 갖는다.
- 이 컬렉션이 다루지 않은 심화 주제(플로팅 패널, 제어 모드, 훅)를 인지하고 필요할 때 공식 문서로 이어갈 수 있다.
- 00장에서 제시한 커리큘럼 전체를 되짚어, 자신에게 부족한 챕터를 다시 찾아 복습할 수 있다.
